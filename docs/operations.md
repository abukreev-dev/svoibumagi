# Локальный запуск и сохранность данных

**Статус:** инструкция для экспериментальной версии. Импорт обоих брокеров ещё проходит сверку; приложение не предназначено для решений о сделках или налогах.

## Запуск для разработки

```sh
python3 -m venv .venv
.venv/bin/pip install -e '.[test]'
.venv/bin/pytest -q
.venv/bin/python -m svoibumagi hash-password
```

Последняя команда запросит пароль дважды и выведет только scrypt-хеш. Сохраните его в переменной `SVOIBUMAGI_PASSWORD_HASH` вне репозитория. Для локальной проверки на том же компьютере:

```sh
SVOIBUMAGI_PASSWORD_HASH='<полученный хеш>' .venv/bin/python -m svoibumagi serve --data-dir ./data --insecure-http
```

Адрес: `http://127.0.0.1:8000`. Режим `--insecure-http` допускается только на loopback. Каталог `data/` содержит исходные брокерские файлы и базу, исключён из Git.

В текущем локальном рабочем каталоге `data/` уже содержит проверенный частичный импорт исходных отчётов. Команда выше открывает именно его; не создавайте новый пустой `data/` поверх него. Перед переносом или экспериментами используйте закрытую актуальную копию `private/owner-ledger-clean.zip` либо создайте новую через `python -m svoibumagi backup`. Спорный отчёт ИИС хранится вне рабочей базы в исходном каталоге и закрытом реестре; шестой неподтверждённый счёт удалён после копирования. Версия до очистки сохранена в `private/owner-ledger-before-quarantine-cleanup.zip`. Общий расчёт остаётся недоступным до разрешения пробелов и принадлежности отчёта. Docker Compose ниже использует отдельный именованный том и автоматически не видит локальный `data/`.

На этом компьютере дополнительно запущен локальный экземпляр через `launchctl submit` с меткой `com.alexanderbukreev.svoibumagi.local` и адресом `http://127.0.0.1:18080`. Он читает `data/`, слушает только `127.0.0.1` и использует HTTP только для локального доступа. Пароль лежит в закрытом файле `private/local-app/login.txt`; хеш и запускной скрипт находятся в той же исключённой из Git папке. Проверить текущий процесс: `launchctl list com.alexanderbukreev.svoibumagi.local` и `curl -f http://127.0.0.1:18080/login -o /dev/null`; остановить: `launchctl remove com.alexanderbukreev.svoibumagi.local`. После перезагрузки компьютера этот пробный сервис может потребовать повторного запуска; `launchctl submit` не является настроенным постоянным LaunchAgent. Изменения в браузере теперь пишутся в `data/`, поэтому перед экспериментами создавайте свежую копию.

Ссылка «Выгрузить разрывы и подтверждения CSV» в обзоре скачивает `/export/gaps.csv` после входа. Строки `uncovered_gap` — дни, которых всё ещё нет в подтверждённой истории; `needs_owner_confirmation` означает, что граничные остатки допускают проверку периода владельцем, `needs_source_or_review` требует дополнительного источника или разбора. Строки `owner_statement` показывают действующие и отозванные подтверждения отдельно. Номер счёта берётся из проведённых отчётов; для спорного или ещё не проведённого счёта он остаётся пустым с явным `account_number_status`.

## Docker Compose и доступ извне

В обзоре форма «Обновить цены всех ненулевых позиций» получает котировки по всем ISIN на выбранную дату. При неизвестном ISIN, неоднозначной бумаге, отсутствии подтверждённой цены или сетевой ошибке весь набор отклоняется без записи. Успешный набор записывается одной транзакцией; одинаковый повтор не создаёт дублей. Допускается до 100 разных бумаг за запрос, одновременно отправляются не более четырёх запросов.

Создайте локальный `.env` со строкой `SVOIBUMAGI_PASSWORD_HASH=<хеш>`; файл исключён из Git. Затем `docker compose up --build -d`. Compose привязывает порт только к `127.0.0.1:18080` на хосте; если он занят, задайте в том же `.env` другой свободный `SVOIBUMAGI_HOST_PORT`. Порт внутри контейнера остаётся `8000`. Для удалённого доступа настройте HTTPS reverse proxy **на том же хосте**: его upstream — `http://127.0.0.1:18080` либо выбранный хостовый порт. Браузер должен обращаться к приложению через HTTPS, чтобы cookie с флагом `Secure` передавался корректно. Сертификат и ключ храните вне репозитория; порт приложения не открывайте в интернет. При размещении прокси на другом хосте используйте защищённый канал до upstream и отдельно настройте доступ к нему.

Для локальной повторной загрузки отчётов без HTTPS-прокси предусмотрен отдельный файл `compose.local-http.yaml`. Он явно отключает флаг `Secure` у cookie только в этом режиме; базовый Compose по-прежнему рассчитан на HTTPS. Применяйте этот файл только на своей машине и только с портом, опубликованным на `127.0.0.1`:

```sh
docker compose -f compose.yaml -f compose.local-http.yaml --env-file private/working-app/.env -p svoibumagi-working up -d --build
```

На текущем компьютере эта команда использует закрытый файл окружения с портом `18081` и отдельный том `svoibumagi-working_svoibumagi_data`. Адрес для входа: `http://127.0.0.1:18081`; пароль тот же, что указан в закрытом `private/local-app/login.txt`. Проверочный синтетический счёт после перезапуска удалён: рабочая база пуста и готова к новой загрузке. Прежняя проверочная база `data/` и сервис на порту `18080` независимы от неё. Для проверки или остановки именно этого экземпляра повторяйте те же `-f`, `--env-file` и `-p` с командами `ps`, `restart` или `stop`; том при `stop` сохраняется. Не используйте локальный HTTP-режим для внешнего доступа.

При отдельном пробном `docker run` со случайным хостовым портом (`127.0.0.1::8000`) после `docker restart` считайте фактический порт заново через `docker port <контейнер> 8000/tcp` или `docker inspect`; Docker может назначить другой. Рекомендуемая Compose-схема выше использует заданный хостовый порт.

На схеме v18 отдельный Compose-проект с синтетическими счётом, ручным событием и проведённым отчётом сохранил данные и исходный файл после перезапуска. Копия из этого контейнера восстановила их в новый каталог; SQLite прошла `quick_check` и проверку внешних ключей. `/login` ответил HTTP 200 после запуска и перезапуска, хостовый порт `18080` публиковался только на `127.0.0.1`. Отдельный Docker-образ v18 также прошёл `pip check`. Для целевого хоста проверки нужно повторить с его конфигурацией после выбора площадки.

Автоматические котировки ISS по умолчанию отключены: ни одна веб-форма не вызывает биржу. Официальная [страница ISS](https://www.moex.com/a2193) ограничивает использование данных ознакомлением без договора, а [индивидуальный доступ](https://www.moex.com/ru/products/personal) требует заявки и акцепта оферты. Применимость этих условий к автоматической оценке частного портфеля не установлена; [разбор и конкретные вопросы Бирже](moex-data-terms.md) сохранены отдельно. До подтверждения права оставьте `SVOIBUMAGI_MOEX_ISS_ENABLED=0`. После оформления применимого доступа оператор может добавить во **вне-Git** `.env` строку `SVOIBUMAGI_MOEX_ISS_ENABLED=1` и пересоздать контейнер. Это технический переключатель, а не подтверждение прав. Ручная цена с датой и источником работает без него.

Котировки ISS загружаются отдельным исходящим HTTPS-запросом только после включения. Если прямое соединение недоступно, добавьте во **вне-Git** `.env` строку `SVOIBUMAGI_ISS_HTTPS_PROXY=http://<доступный-прокси>:<порт>` и пересоздайте контейнер. Compose передаёт значение в `HTTPS_PROXY` процесса; без настройки переменная пуста и запрос идёт напрямую. На текущем macOS Docker Desktop проверен адрес `host.docker.internal` к работающему локальному прокси; `127.0.0.1` внутри контейнера обозначает сам контейнер. На другом хосте нужен свой доступный адрес. Пробный вызов из контейнера должен подтвердить точный ISIN, режим TQBR, дату и положительную цену; сбой обновления не меняет сохранённую цену. Не записывайте данные доступа к прокси в репозиторий.

После включения ISS для проверки доступности на выбранном хосте выполните `docker compose exec -T app python -c 'from svoibumagi.prices import get_moex_share_quote; print(get_moex_share_quote("RU0009029540", "SBER"))'`. Это проверка сетевого пути и одного инструмента; цену для пользовательского портфеля сохраняет только действие в веб-интерфейсе после проверки ISIN и даты.

Пример фрагмента Nginx после выпуска сертификата для выбранного домена (замените имя и пути к сертификату):

```nginx
server {
    listen 443 ssl;
    server_name portfolio.example.org;
    ssl_certificate /etc/letsencrypt/live/portfolio.example.org/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/portfolio.example.org/privkey.pem;

    client_max_body_size 21m;
    location / {
        proxy_pass http://127.0.0.1:18080;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto https;
    }
}
```

Синтаксис примера проверен командой `nginx -t` в одноразовом контейнере `nginx:alpine` с временным локальным сертификатом. Отдельный локальный прогон приложения и Nginx в изолированной Docker-сети подтвердил HTTPS-вход, `Secure`/`HttpOnly` у cookie, отказ 401 без входа, отказ 403 при неверном CSRF, доступ к защищённой странице после входа и отсутствие опубликованного порта приложения. В прогоне upstream был адресом контейнера внутри сети; пример выше рассчитан на Nginx и Compose на одном хосте. После настройки проверьте конфигурацию `nginx -t`, затем примените её штатным способом для вашего хоста. Через публичный HTTPS-адрес проверьте загрузку `/login`, флаги `Secure`, `HttpOnly`, `SameSite=Strict` у cookie формы и сессии, вход и выход, отказ без CSRF, скачивание синтетической резервной копии и отсутствие доступа к выбранному loopback-порту извне. Заголовки приложения запрещают кеширование всех ответов, встраивание страницы в чужой сайт и передачу URL в Referer. Эта инструкция ещё не является проверкой конкретного публичного хоста.

Проверка: `docker compose ps`, `curl -I http://127.0.0.1:18080/login` (или выбранный порт), вход через HTTPS, загрузка синтетического отчёта и проверка после `docker compose restart`. Docker-том `svoibumagi_data` содержит пользовательские файлы и базу. Удаление тома удалит данные.

Импорт принимает отчёт до 20 МБ. Размер всего multipart запроса ограничен с небольшим запасом для полей формы: превышение отклоняется кодом HTTP 413 при чтении запроса, до создания попытки импорта.

Для XLSX дополнительно действуют пределы распаковки: 128 МБ суммарного содержимого ZIP и 1000 записей; для XLS/XLSX — до 1 млн ячеек. Превышение отклоняется до записи импорта в журнал. Эти пределы проверены отрицательными синтетическими файлами; все найденные образцы Альфы проходят.

## Резервная копия и восстановление

Веб-интерфейс отдаёт архив через кнопку «Скачать копию базы и файлов». Команды для локального хранилища:

```sh
.venv/bin/python -m svoibumagi backup --data-dir ./data --output /закрытый/каталог/svoibumagi-backup.zip
.venv/bin/python -m svoibumagi restore --archive /закрытый/каталог/svoibumagi-backup.zip --data-dir ./data-restored
```

Восстановление выполняется только в **новый** каталог, проверяет хеши ZIP-манифеста, связь исходных файлов с SHA-256 в журнале, целостность SQLite и внешние ключи. Если открытие восстановленной схемы завершается ошибкой, новый каталог удаляется. Создание копии также отказывает при отсутствующем или изменённом исходном файле. В архив попадает временный снимок только файлов, на которые ссылается копия базы; перед упаковкой их хеши повторно проверяются, поэтому внешнее изменение оригинала во время записи архива не делает копию несогласованной. После проверки остановите приложение и переключите его на восстановленный каталог или том отдельным эксплуатационным действием. Архив содержит персональные финансовые данные: храните его вне публичных каталогов и передавайте только защищённым способом. Копия создаётся с правами владельца.

При открытии старой версии SQLite-схемы приложение сначала проверяет целостность и создаёт локальную копию `ledger.pre-v<версия>-*.bak` с правами владельца, затем применяет изменения схемы одной транзакцией. Этот файл остаётся в закрытом каталоге данных; после проверенного внешнего резервного копирования и успешной миграции его можно удалить вручную.

Схема v20 добавляет счёту явные поля `currency=RUB` и `status=active`. При переходе с v19 существующие счета получают эти значения без изменения операций и исходных файлов; перед переходом создаётся `ledger.pre-v19-*.bak`. Интерфейс пока не переводит счёт в `closed`.

Текущий Docker-образ v20 дополнительно проверен в отдельном временном контейнере с синтетическим томом: входная страница отвечала до и после рестарта, счёт сохранился, проверки SQLite `quick_check` и внешних ключей прошли, `pip check` не нашёл конфликтов. Временные ресурсы удалены. Эта проба не проверяет конкретный HTTPS-хост и не изменяет рабочий локальный контейнер.

Начиная со схемы v6 подтверждённый импорт связывает локальный счёт с идентификатором договора внутри отчёта. При открытии старой базы приложение восстанавливает эту связь из сохранённых подтверждённых файлов. Если в одном счёте обнаружены разные договоры, открытие останавливается с ошибкой: требуется ручное разделение данных и восстановление из копии; автоматическая переноска событий между счетами не выполняется.

При проверке сделки с номером приложение также ищет уже проведённую сделку того же брокера с тем же номером и точным экономическим содержанием на другом локальном счёте. Совпадение видно в предпросмотре как блокирующий конфликт с источником прежней сделки; форма подтверждения скрыта, а прямой вызов подтверждения целиком откатывается. Требуется выяснить принадлежность договоров. Обнаруженная в закрытых образцах пара отчётов ИИС с разными кодами договора и одинаковыми операциями и остатками остаётся на этой проверке; автоматически объединять договоры или суммировать оба отчёта нельзя. Запись с различающимся содержанием обрабатывается обычной проверкой конфликтов внутри своего счёта.

Схема v7 дополнительно запрещает запись операции или наблюдения с файлом другого счёта либо брокера. Перед миграцией сохранённых данных такая несогласованность проверяется отдельно; при её обнаружении открытие останавливается без изменения старой схемы.

Схема v8 добавляет отдельный неизменяемый журнал ручных денежных событий и сделок. Введите счёт, даты, значения и причину на странице «Операции»; совпадающая корректировка с тем же основанием отклоняется. Она видна в CSV и участвует в расчётах, но не меняет сверку брокерского файла задним числом. Корректировка вне периода подтверждённых отчётов делает итоговый расчёт недоступным. Перед исправлением ошибочной ручной записи восстановите копию или добавьте отдельное обоснованное компенсирующее событие и заново проверьте итоги; прямое изменение строк SQLite запрещено.

Схема v9 ограничивает наблюдения: одно проведённое событие может соответствовать только одной строке конкретного файла. При нескольких одинаковых событиях предпросмотр предлагает выбрать ID и исходный файл/строку каждого кандидата; один ID нельзя назначить двум строкам текущего файла. Миграция старой базы с такой неоднозначной связью останавливается без изменения схемы, чтобы решение было принято по исходным отчётам.

Схема v12 добавляет уникальные связи ручного действия амортизации/погашения с денежной строкой и с парой ISIN/дата. Перед переходом с v11 создаётся закрытая копия базы. В отдельном синтетическом Docker-томе переход v11→v12 сохранил ручную операцию, дал `quick_check=ok`, не нарушил внешние ключи и не создал вторую копию при повторном открытии. Пользовательские данные в этой пробе не использовались.

Начиная с v15 требуется сохранённую строку источника для каждого нового события и наблюдения. Изменение и удаление последней связанной строки блокируются. Перед обновлением v14→v15 автоматически создаётся закрытая копия SQLite; синтетический Docker-том сохранил ручное событие, копию и целостность базы. Старые события без сохранённых строк остаются доступными, их происхождение нужно проверить отдельно. Пользовательская база не обновлялась.

Схема v18 запретила новую привязку одного договора к двум локальным счетам того же брокера и типа; в предпросмотре виден блокирующий конфликт. Разные типы счёта не склеиваются автоматически. Миграция v17→v18 создаёт предварительную копию и сохраняет прежние конфликтные привязки для разбора; команда `scripts/audit_source_provenance.py` показывает числовые ID таких счетов со статусом `incomplete`. Правило v17 по-прежнему запрещает новые брокерские операции и наблюдения с исходной строкой только в неподтверждённой попытке; подтверждение меняет состояние попытки и проводит операции атомарно. Прошли 146 синтетических тестов, полный временный веб-прогон 118 образцов и перезапуск отдельного контейнера v18.

Схема v14 добавила ограничения на изменение происхождения проведённых операций и проверку соответствия инструмента сделке. Перед миграцией v13 создаётся закрытая копия. Выгрузка оценки может отдельно показывать неполную известную стоимость по более ранней позиции. Если единственный оставшийся расчётный вопрос — отдельная дневная комиссия без привязки к сделке, XIRR может иметь `xirr_status=available`, а общий `status` остаётся `unavailable` для FIFO. CSV в таком случае содержит XIRR, денежный остаток и конечную оценку, но оставляет себестоимость и реализованный результат пустыми; `fees_paid_cash_rub` показывает комиссию по денежным строкам.

На точную дату проведённого отчёта приложение дополнительно читает итоговую рублёвую стоимость каждой позиции из сохранённой исходной строки: у Сбера конечная рыночная стоимость плюс НКД, у Альфы конечная стоимость позиции. Этот источник показан как `broker_report` и `broker_report_end_value` в CSV оценки, без выдуманной цены за бумагу. Явно введённая ручная цена на тот же день имеет приоритет. Итог из отчёта не действует на следующий день; тогда нужна датированная цена по обычному правилу свежести. При неполном отчёте стоимость может быть показана, но статус сверки и полный расчёт остаются недоступными.

Вспомогательные локальные выгрузки можно использовать как независимые контроли отдельных брокерских отчётов: `PYTHONPATH=src .venv/bin/python scripts/check_sber_operations_export.py <выгрузка-операций.xlsx> <отчёт-сбера.html>` и `PYTHONPATH=src .venv/bin/python scripts/check_alfa_portfolio_export.py <выгрузка-портфеля.xls> <отчёт-альфы.xls>`. Скрипты проверяют договор и период, где применимо, и выводят только количество совпавших контролей; файлы остаются вне Git. Они не создают события в журнале.

## Ограничения текущего этапа

Для локальной проверки состава будущего дистрибутива сначала выполните `.venv/bin/python scripts/audit_dependency_licenses.py requirements.lock`. Она сверяет версии и локальные лицензионные файлы 22 закреплённых зависимостей; при изменении набора пакетов нужна новая проверка условий использования. Затем установите пакет `build` в среду разработки и выполните `.venv/bin/python -m build --outdir private/release-audit-dist`, затем `.venv/bin/python scripts/audit_release_archive.py --private-registry private/sample-registry.json private/release-audit-dist/*.whl private/release-audit-dist/*.tar.gz`. Параметр реестра необязателен, если закрытых отчётов нет; с ним аудитор ищет в содержимом архива отпечатки, имена файлов и ключи счетов из закрытого реестра. Также проверяются типовые признаки персональных данных в текстовых файлах. Сообщения указывают файл и категорию, но не найденное значение. Исходный архив включает документацию, скрипты, синтетические тесты, Dockerfile, Compose, lock-файл и лицензию; wheel содержит только код приложения, шаблоны и лицензию. Проверка выявляет запрещённые пути и отсутствие обязательных файлов; эвристический поиск не заменяет просмотр содержимого перед распространением. Установленный wheel также нужно проверить на чистой среде. Каталог `private/` исключён из Git и исходного архива; текущие локальные артефакты не являются релизом.

Аудитор дополнительно требует GPL/SPDX-маркер в каждом Python-файле, `License-Expression: GPL-3.0-or-later` в метаданных wheel и исходного архива и текст GPLv3 в файле лицензии. Это проверка технического состава пакетов; правообладателя и окончательные уведомления для выбранного способа распространения нужно утвердить отдельно.

Для установки именно проверенного набора зависимостей используйте `requirements.lock` из исходного архива: в новой Python 3.12-среде сначала `.venv/bin/pip install -r requirements.lock`, затем `.venv/bin/pip install --no-deps private/release-audit-dist/svoibumagi-0.1.0-py3-none-any.whl`, затем `.venv/bin/pip check` и `.venv/bin/python scripts/audit_dependency_licenses.py requirements.lock`. Путь к wheel замените на местонахождение проверенного файла. Команда `pip install` только с wheel разрешает установщику выбрать более новые версии по диапазонам из метаданных; для них предыдущий аудит лицензий и регрессий не действует. В Dockerfile lock-файл уже устанавливается перед пакетом с `--no-deps`.

- Поддержка формата не подтверждается только тем, что файл открылся и отдельные суммы сошлись. Перед подтверждением нужно рассмотреть все расхождения и неизвестные строки.
- Для денежных событий без устойчивого ID из перекрывающихся отчётов требуется решение «повтор» или «новое событие» с причиной.
- Неизвестная цена, неполная история и неподдерживаемые действия остаются видимыми. Текущий обзор показывает известную стоимость бумаг, источник и дату каждой цены; полный расчёт по счёту и общему портфелю доступен только после проверки истории, сверки, FIFO и конечной оценки. Ввод SECID получает последнюю цену акции TQBR через ISS; при выборе даты получает историческое закрытие не старше семи календарных дней. Обе ветки проверены на SBER через локальный HTTPS-прокси; прямое локальное соединение завершилось таймаутом. Поиск по ISIN выбирает единственный актуальный инструмент в поддерживаемом режиме TQBR/TQOB/TQCB; при неоднозначности нужна ручная проверка SECID. Рублёвые облигации TQOB/TQCB можно оценить по историческому закрытию, датированному непогашенному номиналу и НКД; отсутствие любой составляющей оставляет цену неизвестной. Остальные режимы требуют ручной цены. Релизная приёмка впереди.

На текущей схеме v19 подтверждения владельцем периода без операций хранятся в `inactive_periods` с датами, основанием и временем; запись можно отозвать на главной странице. Для разрыва, где соседние остатки совпадают и неизвестные либо известные движения не относятся к промежутку, обзор показывает отдельную форму с точными датами. Она не заменяет проверку владельцем факта отсутствия операций; остальные разрывы остаются в причинах недоступности расчёта без такой формы. Подтверждения попадают в резервную копию SQLite. При миграции v18→v19 создаётся предварительная копия базы. Подтверждение применяется к расчёту только после проверки равенства соседних остатков и отсутствия событий; календарное отсутствие отчёта само по себе не является ошибкой импорта. Синтетическая миграция, резервная копия и восстановление прошли. Отдельный Compose-проект v19 пережил перезапуск с синтетическими счётом, денежным событием и подтверждением периода; `/login` ответил HTTP 200, SQLite v19 прошла `quick_check` и проверку внешних ключей, порт остался на loopback. Временный том удалён после проверки.
