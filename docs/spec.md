# Свои бумаги — SPEC V1

- **Статус:** проект технического решения; конкретные адаптеры зависят от образцов
- **Версия:** 1.0 draft, 9 октября 2026 года
- **Основание:** [PRD](prd.md); выполнение разбито в [ТЗ](backlog.md)

## 1. Архитектура и границы

Python/FastAPI обслуживает серверные шаблоны Jinja2 и формы; SQLite хранится в постоянном томе; файлы — в закрытом каталоге данных. Логические модули: `auth`, `accounts`, `imports` (детекторы и версионированные адаптеры), `ledger`, `reconciliation`, `calculations`, `prices`, `export_backup`, `web`. Адаптер выдаёт нормализованные строки и контрольные итоги, но не рассчитывает портфель. Расчётный слой не зависит от брокера. В первой версии не нужны внешняя очередь, Redis и брокерские API.

В публичном размещении анонимный `GET /` отдаёт статический информационный лендинг без запросов к личной базе. Для владельца с сессией тот же маршрут отдаёт обзор. `GET /login` доступен анонимно; все остальные маршруты данных и экспорта защищены сессией. На `ddl` системный nginx завершает TLS и проксирует приложение через loopback-порт; стандартный серверный режим выставляет `Secure` cookie.

Один запрос импорта имеет состояния `uploaded → parsed → awaiting_review → committed` либо `rejected/unsupported/failed`. Перепроверка исходного файла создаёт новую попытку, но не дублирует подтверждённые события. Предпросмотр не меняет журнал. Подтверждение и запись решений выполняются атомарно.

## 2. Данные и инварианты

| Сущность | Обязательные поля и назначение |
|---|---|
| Account | ID, брокер, тип счёта, название, валюта RUB, статус. Номер договора из исходного отчёта показывается владельцу в закрытом предпросмотре и истории загрузок; техническая привязка использует хеш. Номер не попадает в публичный реестр, логи и релизный пакет. |
| SourceFile | ID, account ID, SHA-256, исходное имя, закрытый путь, размер, дата загрузки, обнаруженный формат/версия, период и статус. Один и тот же хеш в разных счетах не объединяет операции автоматически. |
| ImportAttempt | file ID, версия адаптера, время, статус, количество строк по классам и ошибки. |
| SourceRow | attempt ID, лист/раздел, номер строки или диапазон, сырой фрагмент для локальной диагностики, классификация, предупреждения. Секреты и PII не включать в логи. |
| LedgerEvent | ID, account ID, тип, instrument ID при наличии, дата операции, дата расчёта/поступления, количество, валюта, сумма, цена, комиссия, внешний ID при наличии, канонический ключ, статус, ссылка на SourceRow. Денежные и количественные поля — точные десятичные значения. Для сделки Сбера отдельным полем хранится НКД из исходной строки, включая явный ноль; он не смешивается с чистой суммой сделки. |
| Instrument | Внутренний ID, ISIN/тикер и другие подтверждённые идентификаторы; совпадение только по названию не объединяет бумаги. |
| ReportSnapshot | file ID, дата среза, итоговые позиции и остатки, извлечённые из файла. |
| Reconciliation | file ID, вид, рассчитанное и отчётное значение, разница, допуск, статус `matched/difference/unavailable`, причина/решение пользователя и время. |
| Price | instrument ID, значение, валюта, источник, дата/время цены, время получения, статус; ручная цена помечена отдельно. |
| AuditDecision | пользователь, время, действие, объект, причина; сохраняет разрешение спорного дубля, расхождения или корректировки. |
| ManualEvent | account ID, тип `trade/cash`, нормализованные поля операции, время ввода и обязательная причина; отдельный неизменяемый источник для подтверждённой владельцем корректировки. |

Для V1 валюта счёта хранится явно как `RUB`, статус нового счёта — `active`. Пустой ошибочно созданный счёт можно удалить, только если на него не ссылаются источники, попытки импорта, подтверждения, операции или решения; ограничения внешних ключей проверяются в той же транзакции. Проведённый счёт и его историю удалять нельзя. Схема допускает `closed` как состояние записи, но закрытие счёта и его влияние на импорт и расчёты требуют отдельного правила; интерфейс V1 не меняет статус.

Каждая проведённая операция имеет источник: строку файла либо подтверждённую ручную корректировку с причиной. Ручная корректировка хранится отдельно от брокерского файла, включается в журнал и расчёт, но не меняет историческую сверку исходного отчёта. Совпадающие счёт, событие и причина не создают вторую корректировку. Корректировка вне охвата подтверждённых отчётов блокирует проверенный расчёт. Исходный файл после загрузки неизменяем. Удаление файла, на который ссылается журнал, запрещено без явного каскадного сценария с пересчётом; для V1 доступно удаление только неподтверждённых загрузок. Дата и время хранения — явные, показ пользователю — в выбранной зоне; денежный учёт ведётся в валюте операции без бинарного `float`.

При проверке повтора ручной корректировки десятичные записи одного числа (`100`, `100.00`) равны. Экономическая идентичность ручной сделки определяется датами, ISIN, количеством, ценой, суммой, комиссией и валютой; изменение отображаемого названия бумаги не создаёт вторую сделку с той же причиной. Проверка повтора и запись сериализованы. Канонический ключ брокерского события сохраняет все десятичные цифры без округления по текущему контексту `Decimal`.

SQLite отклоняет новые брокерские и ручные события с некорректным JSON, отсутствующими обязательными полями сделки или денежного движения либо неверным JSON-типом этих полей. Новая брокерская операция и наблюдение дубля дополнительно требуют строку подходящего класса в попытке импорта со статусом `committed`. Подтверждение переводит попытку в `committed` и записывает события в одной транзакции; ошибка откатывает и статус, и журнал. Числовые значения дополнительно проверяются Python-кодом до записи. Миграция сохраняет старые строки без автоматического исправления; их происхождение и полнота проверяются отдельно перед подтверждённым расчётом.

## 3. Контракт адаптера и импорт

1. Детектор проверяет содержимое, известные листы/HTML-таблицы и сигнатуру версии. Расширение — лишь предварительный фильтр. Неизвестная версия возвращает `unsupported`, не меняя журнал.
   Подтверждённый локальный счёт связывается с закрытым хешем однозначного идентификатора договора внутри отчёта. Загрузка и подтверждение отчёта другого договора в этот счёт отклоняются; для Сбера также сверяется тип обычный/ИИС. Новая привязка того же договора к другому локальному счёту того же брокера и типа блокируется при предпросмотре и подтверждении; SQLite отклоняет вставку даже в обход приложения. Совпадение кода между обычным счётом и ИИС не служит основанием для их объединения. Старые подтверждённые файлы проверяются при миграции, а ранее созданные двойные привязки сохраняются для аудита без автоматического слияния. Отсутствующий или неоднозначный идентификатор отклоняет вариант, а старую ожидающую попытку без ключа нужно разобрать заново текущим адаптером.
2. Адаптер выдаёт для каждой значимой строки класс: поддерживаемое событие, итоговая позиция/остаток, служебная строка либо `unparsed` с причиной. Пропуск значимой строки без классификации — ошибка адаптера.
3. Нормализация проверяет даты, знаки, валюту, количество, идентификатор инструмента и связь комиссии со сделкой. Неоднозначность даёт предупреждение и требует решения, а не догадки.
   Отчётный период с датой окончания раньше даты начала отклоняется до сохранения попытки импорта и исходного файла.
   Для XLSX до чтения листов проверяются суммарный распакованный размер и число ZIP-записей; для XLS и XLSX ограничено число ячеек. Превышение даёт явный отказ без записи в журнал. Текущие пределы реализации: 128 МБ распакованных данных, 1000 ZIP-записей и 1 млн ячеек.
4. Тот же файл в том же счёте обнаруживается по хешу. Для перекрывающихся отчётов сначала используется устойчивый ID брокера; при его отсутствии — составной ключ с типом, счётом, датами, инструментом, количеством, суммой и релевантными реквизитами. Разные события с одинаковым составным ключом переходят в спорные дубли и решаются вручную. Номер строки сам по себе не ID события.
   Если несколько строк одного файла имеют одинаковый составной ключ, каждую строку можно связать только с отдельным существующим событием. Предпросмотр показывает исходный файл и строку каждого кандидата; повторное использование одного события для двух строк одного отчёта запрещено.
   Если строка сделки без ID может быть агрегатом нескольких детальных исполнений в другом отчёте, она используется только для проверки арифметики исходного отчёта и явно помечается для ручного сопоставления. Она не записывается как отдельная сделка, пока не доказано, какая часть ещё отсутствует в журнале; остаточную сделку нельзя создавать по одной разнице количеств без проверки суммы, комиссии и источника. После проверки полной суммы и комиссии исходной строки оператор может провести её целиком как агрегированную сделку с причиной и ссылкой на источник. Решение сохраняется в аудите; найденное совпадающее событие блокирует проведение. Без решения по каждой такой строке подтверждение отчёта запрещено.
5. Предпросмотр показывает период, все классы строк, новые/повторные/спорные события, итоговые сверки и последствия подтверждения. Подтверждение запрещено, пока не принято явное решение по каждому материальному неизвестному событию, спорному дублю и расхождению; допускается зафиксированное исключение с причиной и статусом неполноты.
6. Подтверждение повторной загрузки не создаёт новые экземпляры уже проведённых событий. Ошибка разбора или записи откатывает попытку без частичного журнала.

Реестр поддерживаемых форматов содержит брокера, название отчёта, сигнатуру, версию адаптера, набор проверенных событий, наличие итогов, дату и контрольный образец. Пополнение реестра требует локальной проверки обезличенного реального образца и синтетического теста без PII в Git.

## 4. Сверка и полнота

На дату среза отчёта считаются количества по каждому инструменту по сделкам, расчёт по которым состоялся не позже этой даты, и остаток каждой валюты/денежного раздела. Сравнение идёт с отчётными итогами того же счёта и даты. Допуски задаются отдельно для денег и количества на основании формата отчёта и фиксируются в реестре; округлять промежуточные вычисления нельзя. Денежная строка с датой вне заявленного периода остаётся диагностикой с адресом исходной строки и не проводится в журнал автоматически. Для проведённой сделки дата расчёта должна попадать в период отчёта и быть не раньше даты заключения; дата заключения может предшествовать началу периода. Нарушение остаётся диагностикой с адресом строки. Сделки со статусом «заключена, но не исполнена» показываются отдельно и не меняют проведённые позиции. Отсутствие бумаги в таблице позиций не доказывает её нулевой начальный остаток: для сделки по такой бумаге статус сверки `unavailable`. Неизвестный начальный остаток, пропуск периода, неподдерживаемая операция или отсутствие итоговой секции дают `unavailable` или `difference` с причиной, но никогда `matched`.

При выводе итоговой рублёвой себестоимости FIFO и реализованного результата интерфейс и CSV показывают две цифры после запятой. Внутренние значения `Decimal`, распределение себестоимости между частичными продажами и расчёт XIRR сохраняют полную точность; отображение не меняет бухгалтерский результат.

Если брокер приводит отдельные итоги вводов и выводов, они сверяются с соответствующими движениями независимо от общего денежного остатка. Для HTML Сбера на дату расчёта отдельно сверяются чистая сумма сделок с НКД и общая комиссия сделок с денежными списаниями комиссий. Поступление с другого субсчёта может входить в брокерский итог ввода данного счёта; пока не установлен счёт-источник, его внешность для общего портфеля остаётся неизвестной и расчёт доходности не считается проверенным.

Сверка является срезом конкретного файла; более поздний импорт не переписывает прошлый результат. Интерфейс показывает рассчитанное, отчётное, разницу, допуск и статус. Ручное признание расхождения не меняет его на `matched`. Общий портфель помечается неполным, если хотя бы один включённый счёт имеет неразрешённый пробел истории или операции.

За период без операций брокерский отчёт может не формироваться. Владелец вправе подтвердить отсутствие операций за точные включительные даты по конкретному счёту; запись хранит автора, время и основание, отображается отдельно от брокерских файлов и может быть отозвана. Подтверждённый период закрывает пробел активности только в пределах этих дат и только если позиции и деньги в соседних отчётах равны, в журнале нет операций с датой внутри периода и нет неразрешённых строк, способных изменить остатки. Неразрешённая строка соседнего отчёта блокирует закрытие пробела, если её дата неизвестна или попадает в него; строка с подтверждённой датой вне пробела остаётся отдельным препятствием для общего проверенного расчёта, но не отменяет подтверждённые дни без операций. Новый отчёт или операция, противоречащие подтверждению, возвращают блокирующий статус и требуют повторной проверки. Календарное покрытие файлами и доказанная полнота операций показываются раздельно.

## 5. Расчётный контракт

- **Позиция:** количественные изменения по подтверждённым событиям; короткие/отрицательные позиции вне V1 и требуют разбора. Амортизация меняет денежные потоки и остаточную себестоимость по правилам, проверенным на образцах. Погашение закрывает соответствующие партии.
- **FIFO:** партии ведутся по инструменту и счёту в порядке даты расчёта, даты заключения и, если брокер указывает, времени сделки; далее применяется устойчивый tie-breaker по исходной строке. Для согласованного варианта Альфы отсутствие времени или противоположные сделки с одинаковой датой и временем блокируют проверенный FIFO. Себестоимость покупки включает относимую комиссию; выручка продажи уменьшается на относимую комиссию. Частичная продажа делит партию пропорционально без потери остатка. Перевод между своими счетами переносит партии и их себестоимость, не создавая продажи. Спорные даты/комиссии — блокирующие вопросы до утверждения методики.
- **Деньги:** для каждого подтверждённого события определяется подписанное движение денежных средств; начальный остаток допускается только как явно подтверждённая точка отсчёта с датой и происхождением. Остатки не выводятся из текущей стоимости бумаг.
- **Результат:** реализованный результат по чистой цене бумаги отделён от купонов, дивидендов, НКД, комиссий вне сделок и фактически удержанного налога. Подписанное сальдо НКД равно полученному при продаже минус уплаченный при покупке; для Альфы оно берётся из отдельных денежных строк, для Сбера — из поля сделки. Купоны плюс сальдо НКД показываются как денежный показатель без вывода налоговой базы. Налог к будущей уплате не рассчитывается.
- **Стоимость:** на точную дату проведённого отчёта можно брать рублёвую итоговую стоимость каждой позиции из сохранённой исходной строки: у Сбера рыночная стоимость на конец периода плюс НКД, у Альфы конечная стоимость позиции. Количество, ISIN/название и строка источника должны совпасть с проведённой позицией; сумма Альфы дополнительно сверяется с итогом раздела. Это стоимость позиции на дату отчёта, не биржевая цена за штуку: она не переносится на следующие дни и не сохраняется как ручная котировка. Явно заданная ручная цена на ту же дату имеет приоритет. При отсутствии такой стоимости или на иную дату используется количество × последняя применимая цена, если возраст цены не более 7 календарных дней. Для акции TQBR источник ISS может дать последнюю сделку или историческое закрытие `CLOSE` на выбранную дату с явным SECID и проверкой ISIN; это разные методики, сохраняемые в примечании к цене. Автоматический поиск по ISIN принимает только одно актуальное совпадение в поддерживаемом режиме; неоднозначность оставляет цену неизвестной до ручной проверки SECID. Для рублёвой облигации TQOB/TQCB историческая грязная цена за бумагу = `CLOSE` (процент от номинала) × датированный `FACEVALUE` / 100 + датированный `ACCINT`; отсутствие номинала, НКД или подтверждённой сделки блокирует автоматическую цену. Цена имеет источник и дату. Более старая цена остаётся видимой со статусом `stale_price`, но стоимость позиции и проверенный общий итог неизвестны; то же правило действует при отсутствии цены или неподтверждённой идентичности бумаги. Подтверждённая нулевая позиция стоит 0 без котировки. Общая стоимость помечается неполной, неизвестное не подменяется нулём.
- **XIRR:** внешние вводы и выводы с датами плюс конечная оценка на выбранную дату; для отдельного счёта денежный или бумажный перевод между своими счетами считается потоком на границе счёта, для объединённого портфеля — внутренним. Бумажный поток оценивается по подтверждённой рублёвой цене на дату перевода; без неё индивидуальный XIRR недоступен. Перенесённые FIFO-партии сохраняют исходную дату и себестоимость, продажи нет. Расчёт выполняется в `Decimal` или с контролируемой точностью преобразования и проверяется независимыми примерами. Нет полной истории, конечной оценки, смены знака потоков или устойчивого решения — показать причину вместо процента. Нераспределённая по сделкам дневная комиссия блокирует себестоимость FIFO и реализованный результат, но не XIRR при полной сверке денег: сумма комиссии уже входит в конечный денежный остаток. В интерфейсе указать период и состав денежных потоков.

Для общего XIRR цена внутреннего бумажного перевода на дату перевода не нужна: оба плеча исключаются из внешнего потока. Проверяются полная история и конечная рублёвая оценка каждого счёта на одну дату, а корень общего потока вычисляется независимо от индивидуальных XIRR. Если другой блокирующий пробел остаётся, общий XIRR недоступен.

Правила знаков, дат, распределения комиссий, амортизации, погашения и точности оформляются как таблица контрольных случаев до реализации расчётов. Числа из Investbook можно использовать лишь для независимого сравнения результата; его код и тесты не копируются.

## 6. Интерфейс и внешние данные

Экраны: вход; счета; импорт и история; предпросмотр и решение; обзор; позиции; операции с фильтрами и ссылкой на источник; настройки цен, экспорта и копий. На каждом агрегате есть дата расчёта и статус полноты. Сервис котировок получает только публичные идентификаторы инструментов, не отправляет отчёты и сохраняет источник, время, статус обновления. Веб-запросы ISS отключены по умолчанию и включаются приватной конфигурацией после проверки применимых условий доступа; технический переключатель не является подтверждением прав. Сбой цен не изменяет журнал. Неопознанные и неподдерживаемые бумаги допускают ручную цену с датой.

CSV-экспорт содержит нормализованные операции и расчётные таблицы с указанием методики/даты; формула безопасного экспорта экранирует значения, начинающиеся с символов формул. Резервная копия включает консистентную SQLite-базу, исходные файлы и метаданные версии; восстановление проверяет целостность и выполняется в пустое хранилище либо по явной процедуре замены.

В CSV оценки общий `status` дополняется независимыми `report_check_status`, `position_date_status` и `price_status`: отсутствие проверок отчёта не считается совпадением, а устаревшие отчёт и цена видны одновременно. Для счёта без отчёта на выбранную дату все три частных статуса — `unavailable`.

Обзор и CSV операций, позиций, оценки и расчётов показывают `account_number` из содержимого проведённого брокерского отчёта отдельно от локальных `account_id` и названия. Если таких отчётов нет, номер неизвестен. Если проведённые источники одного локального счёта содержат разные номера, обзор сообщает о неоднозначности, CSV оставляет `account_number` пустым, а подтверждённые FIFO и XIRR счёта и портфеля недоступны до разрешения противоречия. Известные денежный остаток и оценка последнего отчёта могут оставаться видимыми со статусом неполноты. Автоматический выбор одного номера запрещён. Поле выводится только после входа владельца.

Обзор может предложить владельцу точные незакрытые даты между отчётами для подтверждения отсутствия операций. Предложение показывается лишь если соседние позиции и деньги совпадают, а известные операции, агрегированные сделки и неразобранные строки не могут относиться к разрыву. Наличие предложения не является доказательством отсутствия операций: запись требует отдельного основания владельца и остаётся отзывной. Для прочих разрывов даты и причина неполноты видны без предлагаемой формы.

При сравнении граничных позиций используются пары ISIN и валюты. Если в одном из соседних отчётов нет таблицы позиций, позиция не имеет ISIN или валюты либо денежный остаток не имеет валюты, подтверждение владельца не закрывает разрыв: равенство неполных словарей не считается доказательством.

В CSV расчётов указанный в отчёте денежный остаток и рассчитанная по доступным ценам стоимость позиций отдельного счёта сохраняются даже при недоступном XIRR, с явным статусом `unavailable` и причиной. Такой остаток не считается независимо сверенным, если сверка денег не прошла. Неизвестное значение остаётся пустым. Общая строка по нескольким счетам не суммирует несовместимые даты и не заполняется оценкой только по части счетов.

Остатки и позиции с валютой, отличной от RUB, не складываются с рублями без подтверждённой конвертации. В рублёвых полях расчёта счёта и CSV их значение пустое; обзор сохраняет позицию и явно показывает необходимость конвертации. Известный рублёвый итог может содержать лишь остальные позиции и помечается неполным.

## 7. Безопасность, запуск и эксплуатация

Один владелец, пароль с современным адаптивным хешированием, серверная сессия, защищённые cookie, CSRF для изменяющих форм, лимит размера и проверка структуры файла. Доступ к исходникам и базе только у процесса приложения; пути загрузки не строятся из имени файла. Диагностика не пишет содержимое отчётов. Рекомендуемый Compose не публикует порт приложения наружу; внешний доступ через HTTPS reverse proxy. Секреты и пользовательские данные лежат вне Git и образа.

Миграции схемы версионированы; перед миграцией есть резервная копия. Тест восстановления обязателен перед релизом. Лицензии выбранных зависимостей фиксируются до включения. Публикация исходников и правообладатель — отдельный релизный шаг.

## 8. Проверка и выпускной барьер

Проверка состоит из синтетических тестов парсера и инвариантов, локальных прогонов обезличенных образцов, контрольной таблицы операций/позиций/денег по каждому отчёту, независимых примеров FIFO/XIRR, сценариев дублей/перекрытия/отката, проверки доступа, рестарта и восстановления. Реальные отчёты и производные PII не попадают в Git, CI и публичные логи.

Статус «поддерживается» присваивается только варианту формата, для которого известны сигнатура и контрольные итоги, классифицированы все значимые строки и проверена сверка. Релиз V1 требует выполнить критерии PRD и закрыть P0/P1 из [ТЗ](backlog.md); непроверенные форматы остаются явно неподдерживаемыми.

Приёмка реализации проводится на согласованном наборе образцов в чистой базе и на синтетических отрицательных сценариях. Рабочая база владельца создаётся отдельно и наполняется им заново после приёмки сервиса. Отсутствие полной истории в проверочном наборе не блокирует готовность загрузки, защиты, экспорта и восстановления; оно блокирует только утверждение полноты конкретного портфеля и проверенного FIFO/XIRR по нему. Спорный файл не проводится автоматически ради закрытия этого статуса.
